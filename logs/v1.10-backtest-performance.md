# v1.10 — backtest performance: three superlinear scans removed (no rule changed)

Date: 2026-09-29
Scope: fix the long-range backtest lag. Three hot paths in the engine pass were
quadratic in the length of the series; all three are now linear. **No shipped
rule changed** — every decision, price and outcome is byte-identical.

Base: `main` @ `56172c0`
Branch: `arena/01a0ee8d-system`
Prior: `logs/v1.9-research-filters.md`

---

## 1. What was slow

Measured on the locked baseline (9,738 candles / 293 days / 155,808 result rows)
and on date-shifted copies of it (the engine pass is `runAnalysis` under
`ANALYZER_CERTIFIED_OPTIONS`):

| Series         | Before    | After    |
| -------------- | --------- | -------- |
| 9,738 candles  | 1,051 ms  | 609 ms   |
| 19,476 candles | 3,113 ms  | 1,230 ms |
| 38,952 candles | 12,884 ms | 2,508 ms |

Per-doubling ratio before: 2.94× then 4.14× (quadratic). After: 1.78× then 2.04×
(linear). `computeHtfTrendContext` alone went 303 ms → 58 ms on the baseline and
5,844 ms → 167 ms at 38,952 candles.

1. **`structure.ts#precomputeTrendsAtCompletions` (the dominant term).** For
   every completed H1/H4/D1 bar it rebuilt the entire prefix pivot list — two
   O(count) scratch arrays plus a full ±2 pivot scan — so the pass was O(bars²).
   The pivot window is a fixed ±2 bars, so a pivot is decided the moment
   `bars[i-2..i+2]` exist and can never be un-confirmed by later bars. The pass
   now walks the bars once and keeps only confirmed pivots. Output per
   completion is unchanged (pinned in `tests/perf-equivalence.test.mjs` against a
   verbatim copy of the old prefix scan, on synthetic bars and on the real
   baseline's H1/H4/D1 aggregates).
2. **`ctx.daily.filter((d) => d.day < day)` in the production strategies and
   filters.** Walked the whole prior-day history and allocated a fresh array once
   per candle per strategy (`final-survivors.ts` PDH-retest and classic pivot;
   `spec-strategies.ts` PDH context tool and the legacy ORB 10-day Stretch;
   `turtle.ts` dHigh/dLlow; `regime-filters.ts` `priorDayPos`). Now a binary
   search over the day keys in `src/lib/analyzer/day-lookup.ts`, with an exact
   fallback to the old filter when the array is not day-ascending — including
   `slice(-n)`'s `-0` quirk.
3. **`status.ts#countForwardValid`.** Walked from every PASS row to the end of
   the file to count valid candles — O(rows × candles) over a run. Now a
   per-array suffix count, same cardinality.

End to end, the page-equivalent local work (engine pass → one-pass day index →
day loop with per-day reports → ZIP) on the golden range and a 4× copy of it:

| Phase     | 293 days / 155,808 rows | 1,169 days / 622,944 rows |
| --------- | ----------------------- | ------------------------- |
| engine    | 777 ms                  | 2,609 ms                  |
| day index | 23 ms                   | 82 ms                     |
| day loop  | 71 ms                   | 240 ms                    |
| ZIP       | 101 ms                  | 400 ms                    |

≈ 3.4–4.0× per 4× data: linear in series length. The backtest day loop itself
was already fixed in the previous pass (one-pass day index;
`buildStrategyBreakdown(rowsForDay)`), which took the golden-window loop from
1,371 ms to ~64 ms.

The page's day loop also now yields to the event loop every 64 days, so Stop and
the progress/current-day readout stay live on a long range instead of only
updating after the whole replay. No step in that loop reads the clock, so the
output is unaffected.

## 2. Why the rule-set freeze moved (and why nothing shipped changed)

`tests/ruleset-freeze.test.mjs` hashes the **sources** of the rule files, so a
pure refactor of those files changes their hashes even when behaviour does not.
Per that test's own re-freeze policy the hashes are re-recorded here, in the same
change, with the evidence that the shipped rule set is untouched.

## 4. Known, deliberate cost that remains

`buildDayReport` is self-contained **by design**: every day file reprints the
cumulative per-strategy table and the "SKIPPED DAYS SO FAR" list. That makes the
packaged output grow with days² (≈ 5.2 MB of reports on the 293-day baseline,
≈ 27.5 MB at 4×) and the ZIP step grows with it. It is report content, not
analysis: cutting it would change what a day file contains, which is a product
decision, so it was left alone.

`run.ts` still computes `perStrategy` with three `results.filter(...)` passes per
strategy (~5% of the engine pass, linear). Left alone in this change to keep the
diff to the frozen files to the three algorithmic fixes; the fetch path
(sequential 90-day chunks, one provider request each) is similarly linear but
provider-bound.
