## 0. Reframing (what this project is)

Recorded in `PROJECT-CHARTER.md` so it governs future work, not just this pass:

> This is **loss-reduction / trade-quality research** on an existing system, not strategy
> discovery. The loop is: existing strategy signal → identify a genuine bad-trade condition
> → reject that candidate → measure the effect on the entire resulting trade book.

Terminology is now fixed: **live analyzer** = the product; **backtest** = historical replay
of the live decision process; **golden baseline** = development/regression laboratory;
**forward data** = validation; **Filter F** = provisional loss-reduction hypothesis.

## 1. Safeguard — 1,000-bar minimum for production analysis

_Why:_ the live answer for the newest bar depends on saturated warm-up (EMA200, the 50-bar
ATR percentile behind Filter C, daily aggregates, dedupe state). Measured on the locked
baseline: 150–800 bar windows change the newest actionable bar's rows; ≥900 bars matches a
full-history run (`tests/warmup-window-sufficiency.test.mjs`).

_Implementation:_ `MIN_PRODUCTION_BARS = 1000` in `src/lib/analyzer/config.ts`, enforced by
the series contract below and applied on both product paths — the live page refuses to
present results, the backtest refuses to replay a book — with the failure surfaced to the
user. The generator reports depth as PASS/WARN against the same constant, so a short pull is
flagged at the point the data is created.

## 2. Safeguard — no hindsight in the AI verifier input

_Why:_ the verifier picks the setup the trader acts on. Three analyzer columns are computed
from bars **after** the row they describe — `similar_swing_retrace_pct` and
`similar_swing_continued_pct` (40-bar forward window) and `swing_invalidated` ("any later
row") — so a verdict reached on historical data cannot be reproduced live, where those
values do not exist yet.

_Implementation:_ `src/lib/verifier-input.ts` blanks exactly those three columns, preserving
the header, row count and every other cell; `verifier.server.ts` applies it before building
the prompt and appends a note saying the columns were omitted because they are not knowable
at decision time. The system prompt no longer instructs the model to use the retracement
percentage, and instead judges limit-entry distance from the swing levels that
`similar_swing_refs` (causal, earlier rows) actually point at.

_Evidence it is safe:_ the engine's decisions are independent of the three columns —
blanking them over the locked baseline reproduces the trade rows and the series contract
byte-for-byte (`tests/verifier-hindsight-strip.test.mjs`).

## 3. Safeguard — hard validation of unresolved swing refs and trend collapse

_Why:_ `candle.trend` comes from the generator's `similar_swing_refs`, and both filters plus
every trend-aware strategy read it. Refs that do not resolve contribute nothing: a
re-timestamped or spliced file loses **all** of them, every row becomes "ranging", and the
counter-trend layer silently stops firing. Nothing in the pipeline noticed.

_Root cause found while auditing:_ the generator computes refs on the full enriched working
set but omits whole UTC weekend days from the export, so the file it writes contains refs it
does not contain rows for. Measured on the locked baseline: **3,039 of 44,652 refs (6.8 %),
all into weekend days.**

_Implementation, both sides of the contract:_

| Where                  | What                                                                                                                                                                                                                                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Generator (production) | `pruneSwingRefsToExport` drops refs that will not resolve in the file being written (fail-closed: a removed ref can only reduce trend information), clearing the derived swing columns when a row is emptied so the exporter's own invariant (`refs.length > 0 === retrace !== null`) still holds.            |
| Generator (validation) | New report line **“Swing references resolve in-file”**, computed over the rows actually exported; any ref that still dangles fails the export (it means a row was dropped by something other than the documented weekend policy — a hole). New line **“History depth”** (PASS/WARN vs `MIN_PRODUCTION_BARS`). |
| Analyzer (production)  | `src/lib/analyzer/series-contract.ts` inspects every analysed series and reports depth, ref resolution (inside-range vs before-start), trend-capable share and trend distribution. `runAnalysis` attaches it as `analysis.contract`; the live page and the backtest **refuse** a series that fails.           |

_Thresholds_ (collapse detector, not a quality score; calibrated against the baseline's
6.8 % unresolved refs / 92.7 % trend-capable / 87.7 % non-ranging): fail above **50 %**
unresolved refs, below **50 %** trend-capable rows, or below **25 %** non-ranging rows; warn
above 15 % unresolved.

## 4. Safeguard — confirm and preserve live/backtest parity

_Confirmed:_ already pinned by `tests/analyzer-config-parity.test.mjs` (the two shipped
configurations differ in exactly one field; no `src/` call site outside `run.ts` may toggle a
filter; entry points use the shared config objects; the two configs differ only on the final
row of the locked baseline) and by `tests/backtest-analyzer-parity.test.mjs` (row-for-row,
day-supplied accounting, no lookahead, state isolation). Both now import
`ANALYZER_LIVE_OPTIONS` / `ANALYZER_CERTIFIED_OPTIONS` instead of re-typing option literals.

_Preserved by freezing:_ `tests/ruleset-freeze.test.mjs` hashes the normalised source of the
rule files (`regime-filters.ts`, `run.ts`, `final-survivors.ts`, `structure.ts`, `status.ts`)
and fails on any change. Comment and formatting edits are free; a threshold, ordering or
predicate edit fails until someone updates the frozen hash — which the test requires to be a
documented decision (`logs/` + a new evaluation window, per `FORWARD-VALIDATION.md` §2).
Mutation-tested: changing `MOMENTUM_BODY_MIN` 0.8 → 0.85 fails with the frozen-vs-now pair.

## 7. What happens next

Forward validation only (`FORWARD-VALIDATION.md`): collect data after 2026-08-20, run
`scripts/research/validate-on-new-data.mjs`, and let the pre-registered criteria decide.
No new filters, no threshold tuning, no strategy edits against the golden baseline.

removal is a one-flag change plus a golden re-baseline. If it survives, it stays and the next
recurring loss class can be investigated the same way.
