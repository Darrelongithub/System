## 1. Defect — page defaults came from the browser clock, not EAT

`src/pages/DataGenerator.tsx` defaulted its four date fields (chart start/end, OHLC
start/end) and the analysis snapshot's `createdAt` with `format(new Date(), …)`, i.e.
the **browser's** local calendar day, and `src/pages/Backtest.tsx` carried its own
second, independently maintained EAT clock (`Intl.DateTimeFormat` + `formatToParts`)
for the same purpose.

EAT is a fixed **UTC+03:00** offset with no DST, and everything else on those pages
already agrees with it: the header shows an EAT clock, `formatEATTime()` stamps the
log, the snapshot is labelled EAT, and the provider is queried for `Africa/Nairobi`.
A client west of UTC+3 (London in winter, New York, or any UTC-5..-10 browser) still
reads _yesterday's_ local date for the first hours of the EAT day, so a one-click
"latest data" run defaulted to the previous EAT day — a series ending one bar-day
before the newest available data, silently.

Also fixed in the same pass: a `12:00 EAT` label is not the only way to get a
contradictory timestamp/session pair, but the audit that followed showed the
opening-range builder was already fail-closed (see §3).

## 2. Fix

- New `todayEat(nowMs = Date.now())` in `src/lib/analyzer/time.ts`: exact `+3h`
  arithmetic from the epoch, no locale/ICU lookup (consistent with every other
  helper in that file, and provably DST-free).
- `DataGenerator.tsx`: the four `useState` defaults and the snapshot `createdAt`
  route through `todayEat()`.
- `Backtest.tsx`: the local `today()` helper is deleted; `fromDate` / `toDate`
  defaults, the "today" clamp on the resolution window and the day-supplied
  accounting path all use `todayEat()`.

Behaviourally this changes _which_ window a default run requests on a non-EAT
browser clock; it does not change analysis of any given CSV, so no golden row moves.

## 3. Audited and left alone — contradictory `session` vs timestamp

The NY session runs 16:00–00:59 EAT, so its tail hour is keyed to the previous EAT
day and a row whose `session` column disagrees with its own timestamp keys to an
existing range. Checked directly against `minutesIntoSession` before changing
anything: it **wraps** past midnight, so a midday "ny" row reports 1,200 minutes
elapsed, and a morning "london" row 1,320 — both far outside the 30-minute opening
window (`CRABEL_ORB_WINDOW_MINUTES`), so `openingRanges` neither merges them nor
creates a range from them. A guard was written, then reverted once the probe showed
it was unreachable. The behaviour is now pinned by tests instead
(`tests/eat-clock.test.mjs` case 4), so a future change to the wrap cannot quietly
start widening ORB levels.

## 4. Tests

New `tests/eat-clock.test.mjs` (4 tests, registered in `tests/run.mjs`):

1. `todayEat` flips exactly at EAT midnight, incl. July, year rollover and leap day.
2. Source contract: `DataGenerator` no longer defaults from `format(new Date(), …)`,
   uses `todayEat()` for defaults and the snapshot, and `Backtest` uses the shared
   helper and carries no second `Intl.DateTimeFormat` clock.
3. `minutesIntoSession` wraps rather than going negative (the reason the builder's
   window test, not a sign test, is the correct guard).
4. A contradictory session label cannot widen an opening range or create a phantom
   one; a genuine NY tail row resolves to its true opening day.
